# Character appearance and wardrobe consistency

This document describes the deterministic appearance/wardrobe contract used by the
RAAT KA KHAUF pipeline. It is an **offline prompt and validation contract**. It does not add
reference-conditioned generation, image-to-image conditioning, or any credit-bearing step.

## Why the contract exists

Legacy projects store one `look_summary` string per character. That sentence was previously reused
as physical identity, clothing, expression and pose. In scenes it could leak reference-sheet wording
such as “neutral 3/4 pose” and it allowed the same character to be described with different clothes
in different scenes.

The new contract separates:

- **physical identity** (`appearance_lock`) — age, gender, build, skin, face, hair, facial hair, marks;
- **clothing** (`wardrobe`) — named outfits with exact garment slots;
- **scene intent** (`scene.outfit_ids`) — an optional explicit outfit change for that scene.

`look_summary` and `full_prompt` remain reference-sheet metadata. They are still used to generate the
character cutout, but they are **not** the source of scene clothing in strict mode.

## Version gate and modes

New projects created by `scripting/pipeline/one_minute.py` set:

```json
"wardrobe_schema_version": 1
```

`detectWardrobeMode()` selects the mode deterministically:

- **strict** when `wardrobe_schema_version >= 1`, or when any character declares `appearance_lock`
  or `wardrobe`;
- **legacy** otherwise.

A partially migrated manifest therefore cannot silently fall back to legacy behaviour. If one
character declares the new fields, the project is strict and every character must satisfy the
contract.

Legacy projects keep the historical inline prompt hardening and are not rewritten or regenerated by
this work.

## Manifest shape

### Character

```json
{
  "tag": "@CHAR-01-ARJUN",
  "name": "Arjun",
  "age": 22,
  "gender": "male",
  "look_summary": "Reference-sheet description retained for the character asset.",
  "full_prompt": "Reference-sheet prompt retained for the character asset.",
  "appearance_lock": {
    "age": "22-year-old adult Indian man",
    "gender": "male",
    "build": "medium build",
    "skin": "medium brown skin",
    "face": "oval face, clean-shaven",
    "hair": "short black hair",
    "facial_hair": "none",
    "marks": "none"
  },
  "wardrobe": {
    "default_outfit": "nightwear",
    "outfits": {
      "nightwear": {
        "label": "sleepwear",
        "top": "steel grey cotton t-shirt",
        "bottom": "navy blue pyjama trousers",
        "outerwear": "none",
        "footwear": "barefoot",
        "accessories": "none",
        "notes": "loose comfortable fit"
      }
    }
  }
}
```

Rules:

- `appearance_lock` is physical identity only. Do not put clothing, expression, pose, camera
  direction, reference-sheet wording, or “neutral 3/4 pose” in it.
- `wardrobe.outfits` must be a non-empty object, and `default_outfit` must name one of its entries.
- Every outfit must have garment data. Use `none` for an intentionally empty slot.
- Outfit ids should be stable lowercase snake_case.
- Expression and pose are **not** wardrobe fields. The character reference sheet uses neutral
  constants; scenes get their action and camera from the scene itself.

### Scene outfit override

```json
{
  "scene_number": 12,
  "character_tags": ["@CHAR-01-ARJUN"],
  "outfit_ids": {
    "@CHAR-01-ARJUN": "rain_coat"
  }
}
```

`outfit_ids` is optional and is only for an **intentional, scripted** outfit change. The key must be
a character tag that is present in the same scene. The value must be an outfit id declared in that
character's wardrobe. Omit `outfit_ids` (or use `{}`) when the default outfit applies.

The scene prose must not improvise a garment or colour. If the script truly changes clothes, add an
explicit outfit entry and select it with `outfit_ids`. Do not write “Arjun is wearing a red shirt”
unless `red shirt` is in the selected canonical outfit.

### Age and body variants

Use a **separate character tag** for a younger/child version:

```json
{
  "tag": "@CHAR-05-YOUNG-ARJUN",
  "appearance_lock": { "age": "8-year-old Indian child", "build": "small child build", ... },
  "wardrobe": { "default_outfit": "play_clothes", "outfits": { ... } }
}
```

Do not reuse the adult tag and describe it as a child. The strict validator detects an adult
`appearance_lock` being portrayed as a child in scene prose and fails closed.

## Prompt flow

1. **Python** (`scripting/pipeline/one_minute.py`) emits the structured fields and the canonical
   `#BGD-*` / `@CHAR-*` identifiers in the animation prompt. It does not pre-resolve character
   identity into competing prose. The human-readable `still_image_prompt` uses the explicit
   appearance and the exact resolved outfit, and it never contains machine tags or reference-sheet
   pose language.
2. **TypeScript hardening** (`flowPromptHardening.ts`) is the single renderer of canonical ids into
   scene-facing descriptions.
3. **Scene prompt builder** (`sceneFlowWorkflow.buildFlowScenePrompt`) appends the authoritative
   character lock block and the wardrobe continuity restraints. It strips reference-sheet phrases,
   validates scene outfit overrides, and rejects contradictory scene prose.
4. **First clip** (`firstClipLifecycle.ts`) selects the prompt variant by speaker:
   - `NARRATOR`, `none`, `NOBODY`, or a missing speaker with legacy metadata →
     `animation_prompt_NARRATOR_ONLY`;
   - a character speaker → `animation_prompt_WITH_lipsync`.
   An explicit speaker never silently borrows the other variant.
5. **Runner** (`runner.ts`) reads the canonical lower-case `animation_prompt_WITH_lipsync`, builds
   the hardened prompt before `generateProjectVideo`, and never submits raw identifiers.

Strict hardening has two layers:

- `hardenFlowPrompt` resolves `ACTIVE ENVIRONMENT` / `ACTIVE CHARACTERS` from explicit identity
  data. In strict mode it uses `appearance_lock` only and does not inline clothing.
- `buildFlowScenePrompt` adds the scene-specific wardrobe lock, so an intentional `outfit_ids`
  selection is authoritative for that scene.

## Fail-closed codes

Strict generation does not guess, strip, or substitute missing data. Typical codes:

| Code | Meaning |
| --- | --- |
| `APPEARANCE_MISSING` | A strict character has no usable `appearance_lock`. |
| `WARDROBE_MISSING` | A strict character has no wardrobe/outfits map. |
| `WARDROBE_DEFAULT_UNKNOWN` | `default_outfit` is absent or not in `outfits`. |
| `WARDROBE_OUTFIT_UNKNOWN` | A scene selects an outfit id that does not exist (or an empty selection). |
| `WARDROBE_OUTFIT_EMPTY` | The selected outfit has no garment data, or is not an object. |
| `WARDROBE_SCENE_OVERRIDE_UNKNOWN_CHARACTER` | `outfit_ids` names a character not declared in the scene. |
| `WARDROBE_CONTRADICTION` | Scene prose names a garment/colour absent from the selected outfit. |
| `IDENTITY_VARIANT_CONTRADICTION` | An adult character is written as a child without a separate variant tag. |
| `REFERENCE_SHEET_LANGUAGE` | Explicit identity/wardrobe data contains reference-sheet-only wording. |

The generated error text names the character, scene and outfit where available.

## Legacy compatibility

Legacy manifests remain valid:

- `detectWardrobeMode` returns `legacy`;
- `hardenFlowPrompt` keeps the historical byte-for-byte inline `look_summary` hardening;
- no character lock block is appended;
- the character reference sheet keeps using the legacy prompt, with clothing sanitized and neutral
  expression/pose constants for the spec fields.

Legacy projects are not automatically upgraded and are not regenerated.

## Operator checklist

Before a strict project is generated:

1. Confirm `wardrobe_schema_version` is `1` for new projects.
2. Confirm every character has `appearance_lock` and a non-empty `wardrobe.outfits`.
3. Confirm `default_outfit` names an existing outfit.
4. Review every `outfit_ids` entry against the scene's `character_tags`.
5. If the script changes clothing, add the canonical outfit first, then select it.
6. If the script needs a younger/child version, add a separate `@CHAR-*` variant with its own
   identity and wardrobe.
7. Remove reference-sheet wording (“neutral 3/4 pose”, “reference sheet”, “grey studio background”)
   from scene-facing action/camera/effects prose.

Do not fix a contradiction by weakening the validator or by editing generated artifacts. Correct the
manifest and let the deterministic prompt builder run again.
